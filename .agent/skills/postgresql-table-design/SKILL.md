# Diseño de Tablas en PostgreSQL

## Reglas Principales

- Define una **PRIMARY KEY** (clave primaria) para las tablas de referencia (usuarios, pedidos, etc.). No siempre es necesaria para datos de series temporales, eventos o registros (logs). Cuando se use, prefiere `BIGINT GENERATED ALWAYS AS IDENTITY`; usa `UUID` solo cuando se necesite unicidad global u opacidad.
- **Normaliza primero (hasta 3NF)** para eliminar la redundancia de datos y las anomalías de actualización; desnormaliza **solo** para lecturas medidas y de alto retorno de inversión (ROI) donde se demuestre que el rendimiento de los joins es problemático. La desnormalización prematura crea una carga de mantenimiento.
- Añade **NOT NULL** en todos los lugares donde se requiera semánticamente; usa **DEFAULT**s para valores comunes.
- Crea **índices para las rutas de acceso que realmente consultes**: PK/unique (automático), **columnas FK (¡manual!)**, filtros/ordenamientos frecuentes y claves de join.
- Prefiere **TIMESTAMPTZ** para el tiempo de los eventos; **NUMERIC** para el dinero; **TEXT** para las cadenas; **BIGINT** para los valores enteros, **DOUBLE PRECISION** para los decimales (o `NUMERIC` para aritmética decimal exacta).

## "Gotchas" (Cosas a tener en cuenta) en PostgreSQL

- **Identificadores**: sin comillas → se pasan a minúsculas. Evita nombres con comillas o con mayúsculas/minúsculas mezcladas. Convención: usa `snake_case` para los nombres de tablas y columnas.
- **Unique + NULLs**: UNIQUE permite múltiples NULLs. Usa `UNIQUE (...) NULLS NOT DISTINCT` (PG15+) para restringir a un solo NULL.
- **Índices en FK**: PostgreSQL **no** indexa automáticamente las columnas FK. Añádelos tú mismo.
- **Sin coerciones silenciosas**: los desbordamientos de longitud/precisión lanzan error (no hay truncamiento). Ejemplo: insertar 999 en un `NUMERIC(2,0)` falla con error, a diferencia de otras bases de datos que truncan o redondean silenciosamente.
- **Las secuencias/identidades tienen huecos** (es normal; no intentes "arreglarlo"). Los rollbacks, fallos y transacciones concurrentes crean huecos en las secuencias de ID (1, 2, 5, 6...). Este es el comportamiento esperado—no intentes que los IDs sean consecutivos.
- **Almacenamiento Heap**: no hay PK clúster por defecto (a diferencia de SQL Server o MySQL InnoDB); `CLUSTER` es una reorganización puntual, no se mantiene en inserciones posteriores. El orden de las filas en el disco es el orden de inserción a menos que se clústere explícitamente.
- **MVCC**: las actualizaciones (updates) y eliminaciones (deletes) dejan tuplas muertas; el proceso Vacuum las maneja—diseña para evitar una rotación excesiva de filas anchas "calientes" (hot).

## Tipos de Datos

- **IDs**: se prefiere `BIGINT GENERATED ALWAYS AS IDENTITY` (también está bien `GENERATED BY DEFAULT`); `UUID` cuando se fusionen/federen datos, se use en un sistema distribuido o para IDs opacos. Genera con `uuidv7()` (preferido si usas PG18+) o `gen_random_uuid()` (si usas una versión anterior de PG).
- **Enteros**: prefiere `BIGINT` a menos que el espacio de almacenamiento sea crítico; `INTEGER` para rangos más pequeños; evita `SMALLINT` a menos que sea estrictamente necesario.
- **Decimales**: prefiere `DOUBLE PRECISION` sobre `REAL` a menos que el espacio sea crítico. Usa `NUMERIC` para aritmética decimal exacta.
- **Cadenas (Strings)**: prefiere `TEXT`; si necesitas límites de longitud, usa `CHECK (LENGTH(col) <= n)` en lugar de `VARCHAR(n)`; evita `CHAR(n)`. Usa `BYTEA` para datos binarios. Las cadenas grandes o datos binarios (>2KB de umbral por defecto) se almacenan automáticamente en TOAST con compresión. Almacenamiento TOAST: `PLAIN` (sin TOAST), `EXTENDED` (comprimir + fuera de línea), `EXTERNAL` (fuera de línea, sin comprimir), `MAIN` (comprimir, mantener en línea si es posible). El predeterminado `EXTENDED` suele ser el óptimo. Controla con `ALTER TABLE tbl ALTER COLUMN col SET STORAGE strategy` y `ALTER TABLE tbl SET (toast_tuple_target = 4096)` para el umbral. Insensibilidad a mayúsculas: para manejo de locales/acentos usa colaciones no deterministas; para ASCII plano usa índices de expresión sobre `LOWER(col)` (preferido a menos que la columna necesite PK/FK/UNIQUE insensible a mayúsculas) o `CITEXT`.
- **Dinero**: `NUMERIC(p,s)` (nunca float).
- **Tiempo**: `TIMESTAMPTZ` para marcas de tiempo; `DATE` solo para fechas; `INTERVAL` para duraciones. Evita `TIMESTAMP` (sin zona horaria). Usa `now()` para la hora de inicio de la transacción, `clock_timestamp()` para la hora real actual.
- **Booleanos**: `BOOLEAN` con restricción `NOT NULL` a menos que se requieran valores de tres estados (tri-state).
- **Enums**: `CREATE TYPE ... AS ENUM` para conjuntos pequeños y estables (ej. estados de EE. UU., días de la semana). Para valores que dependen de la lógica de negocio y evolucionan (ej. estados de un pedido) → usa TEXT (o INT) + CHECK o una tabla de búsqueda (lookup table).
- **Arrays**: `TEXT[]`, `INTEGER[]`, etc. Úsalos para listas ordenadas donde vayas a consultar elementos. Indexa con **GIN** para consultas de contención (`@>`, `<@`) y solapamiento (`&&`). Acceso: `arr[1]` (índice basado en 1), `arr[1:3]` (segmentación/slicing). Buenos para etiquetas, categorías; evítalos para relaciones—usa tablas de unión (junction tables) en su lugar. Sintaxis literal: `'{val1,val2}'` o `ARRAY[val1,val2]`.
- **Tipos de Rango**: `daterange`, `numrange`, `tstzrange` para intervalos. Admiten solapamiento (`&&`), contención (`@>`), operadores. Indexa con **GiST**. Buenos para programación, versionado, rangos numéricos. Elige un esquema de límites y úsalo consistentemente; prefiere `[)` (inclusivo/exclusivo) por defecto.
- **Tipos de Red**: `INET` para direcciones IP, `CIDR` para rangos de red, `MACADDR` para direcciones MAC. Admiten operadores de red (`<<`, `>>`, `&&`).
- **Tipos Geométricos**: `POINT`, `LINE`, `POLYGON`, `CIRCLE` para datos espaciales 2D. Indexa con **GiST**. Considera **PostGIS** para características espaciales avanzadas.
- **Búsqueda de Texto**: `TSVECTOR` para documentos de búsqueda de texto completo, `TSQUERY` para consultas de búsqueda. Indexa `tsvector` con **GIN**. Especifica siempre el idioma: `to_tsvector('spanish', col)` y `to_tsquery('spanish', 'query')`. Nunca uses las versiones de un solo argumento. Esto se aplica tanto a las expresiones de índice como a las consultas.
- **Tipos de Dominio**: `CREATE DOMAIN email AS TEXT CHECK (VALUE ~ '^[^@]+@[^@]+$')` para tipos personalizados reutilizables con validación. Impone restricciones en varias tablas.
- **Tipos Compuestos**: `CREATE TYPE direccion AS (calle TEXT, ciudad TEXT, codigo_postal TEXT)` para datos estructurados dentro de columnas. Acceso con la sintaxis `(col).campo`.
- **JSONB**: preferido sobre JSON; indexa con **GIN**. Úsalo solo para atributos opcionales o semiestructurados. SOLO usa JSON si se DEBE preservar el orden original de los contenidos.
- **Tipos de Vectores**: tipo `vector` de `pgvector` para búsqueda de similitud de vectores para embeddings.

### No uses los siguientes tipos de datos:

- NO uses `timestamp` (sin zona horaria); USA `timestamptz` en su lugar.
- NO uses `char(n)` o `varchar(n)`; USA `text` en su lugar.
- NO uses el tipo `money`; USA `numeric` en su lugar.
- NO uses el tipo `timetz`; USA `timestamptz` en su lugar.
- NO uses `timestamptz(0)` ni ninguna otra especificación de precisión; USA `timestamptz` en su lugar.
- NO uses el tipo `serial`; USA `generated always as identity` en su lugar.

## Tipos de Tablas

- **Regulares**: por defecto; totalmente duraderas, con registros de logs.
- **TEMPORARY**: ámbito de sesión, se eliminan automáticamente, sin logs. Más rápidas para trabajo temporal.
- **UNLOGGED**: persistentes pero no seguras ante fallos de sistema (crash-safe). Escrituras más rápidas; buenas para cachés o staging.

## Seguridad a Nivel de Fila (RLS)

Habilítala con `ALTER TABLE tbl ENABLE ROW LEVEL SECURITY`. Crea políticas: `CREATE POLICY acceso_usuario ON pedidos FOR SELECT TO usuarios_app USING (id_usuario = id_usuario_actual())`. Control de acceso basado en usuario integrado a nivel de fila.

## Restricciones (Constraints)

- **PK (Clave Primaria)**: implícitamente UNIQUE + NOT NULL; crea un índice B-tree.
- **FK (Clave Foránea)**: especifica la acción `ON DELETE/UPDATE` (`CASCADE`, `RESTRICT`, `SET NULL`, `SET DEFAULT`). Añade un índice explícito en la columna de referencia—acelera los joins y evita problemas de bloqueo en eliminaciones/actualizaciones del padre. Usa `DEFERRABLE INITIALLY DEFERRED` para dependencias FK circulares comprobadas al final de la transacción.
- **UNIQUE**: crea un índice B-tree; permite múltiples NULLs a menos que se use `NULLS NOT DISTINCT` (PG15+). Comportamiento estándar: se permiten `(1, NULL)` y `(1, NULL)`. Con `NULLS NOT DISTINCT`: solo se permite un `(1, NULL)`. Prefiere `NULLS NOT DISTINCT` a menos que necesites específicamente NULLs duplicados.
- **CHECK**: restricciones locales a la fila; los valores NULL pasan la comprobación (lógica de tres valores). Ejemplo: `CHECK (precio > 0)` permite precios NULL. Combina con `NOT NULL` para obligar: `precio NUMERIC NOT NULL CHECK (precio > 0)`.
- **EXCLUDE**: evita valores que se solapen usando operadores. `EXCLUDE USING gist (id_habitacion WITH =, periodo_reserva WITH &&)` evita la sobreventa de habitaciones. Requiere un tipo de índice adecuado (a menudo GiST).

## Indexación

- **B-tree**: predeterminado para consultas de igualdad/rango (`=`, `<`, `>`, `BETWEEN`, `ORDER BY`).
- **Compuesto**: el orden importa—el índice se usa si hay igualdad en el prefijo más a la izquierda (`WHERE a = ? AND b > ?` usa un índice en `(a,b)`, pero `WHERE b = ?` no). Pon primero las columnas más selectivas o las filtradas con más frecuencia.
- **Recubrimiento (Covering)**: `CREATE INDEX ON tbl (id) INCLUDE (nombre, email)` - incluye columnas que no son clave para escaneos solo de índice (index-only scans) sin visitar la tabla.
- **Parcial**: para subconjuntos muy consultados (`WHERE estado = 'activo'` → `CREATE INDEX ON tbl (id_usuario) WHERE estado = 'activo'`). Cualquier consulta con `estado = 'activo'` puede usar este índice.
- **Expresión**: para claves de búsqueda calculadas (`CREATE INDEX ON tbl (LOWER(email))`). La expresión debe coincidir exactamente en la cláusula WHERE: `WHERE LOWER(email) = 'usuario@ejemplo.com'`.
- **GIN**: contención/existencia de JSONB, arrays (`@>`, `?`), búsqueda de texto completo (`@@`).
- **GiST**: rangos, geometría, restricciones de exclusión.
- **BRIN**: para datos muy grandes y ordenados de forma natural (series temporales)—mínima sobrecarga de almacenamiento. Efectivo cuando el orden de las filas en el disco se correlaciona con la columna indexada (orden de inserción o después de `CLUSTER`).

## Particionado

- Úsalo para tablas muy grandes (>100M de filas) donde las consultas filtren consistentemente por la clave de partición (a menudo fecha/hora).
- Uso alternativo: para tablas donde las tareas de mantenimiento de datos lo dicten, ej. datos purgados o reemplazados masivamente de forma periódica.
- **RANGE**: común para series temporales (`PARTITION BY RANGE (fecha_creacion)`). Crear particiones: `CREATE TABLE logs_2024_01 PARTITION OF logs FOR VALUES FROM ('2024-01-01') TO ('2024-02-01')`. **TimescaleDB** automatiza el particionado basado en tiempo o ID con políticas de retención y compresión.
- **LIST**: para valores discretos (`PARTITION BY LIST (region)`). Ejemplo: `FOR VALUES IN ('us-east', 'us-west')`.
- **HASH**: para una distribución uniforme cuando no hay una clave natural (`PARTITION BY HASH (id_usuario)`). Crea N particiones con módulo.
- **Exclusión de restricciones**: requiere restricciones `CHECK` en las particiones para que el planificador de consultas pueda podar (pruning). Se crean automáticamente para el particionado declarativo (PG10+).
- Prefiere el particionado declarativo o las hipertables. NO uses herencia de tablas.
- **Limitaciones**: no hay restricciones UNIQUE globales—incluye la clave de partición en la PK/UNIQUE. No se admiten FKs desde tablas particionadas; usa disparadores (triggers).

## Consideraciones Especiales

### Tablas con muchas Actualizaciones (Update-Heavy)

- **Separa las columnas "calientes" (hot) de las "frías" (cold)**: pon las columnas que se actualizan con frecuencia en una tabla separada para minimizar el hinchamiento (bloat).
- **Usa `fillfactor=90`** para dejar espacio para las actualizaciones HOT que evitan el mantenimiento de índices.
- **Evita actualizar columnas indexadas**: esto impide las actualizaciones HOT beneficiosas.
- **Particiona por patrones de actualización**: separa las filas que se actualizan frecuentemente en una partición diferente de los datos estables.

### Cargas de trabajo con muchas Inserciones (Insert-Heavy)

- **Minimiza los índices**: crea solo lo que consultes; cada índice ralentiza las inserciones.
- **Usa `COPY` o `INSERT` de múltiples filas** en lugar de inserciones de una sola fila.
- **Tablas UNLOGGED** para datos de staging que se puedan reconstruir: escrituras mucho más rápidas.
- **Difiere la creación de índices** para cargas masivas: elimina el índice, carga los datos y vuelve a crear los índices.
- **Particiona por tiempo o hash** para distribuir la carga. **TimescaleDB** automatiza el particionado y la compresión de datos con muchas inserciones.
- **Usa una clave natural como clave primaria**, como por ejemplo (timestamp, id_dispositivo), si imponer la unicidad global es importante; muchas tablas con muchas inserciones no necesitan una clave primaria en absoluto.
- Si necesitas una clave subrogada, **prefiere `BIGINT GENERATED ALWAYS AS IDENTITY` sobre `UUID`**.

### Diseño amigable para Upserts (Insert or Update)

- **Requiere un índice UNIQUE** en las columnas objetivo del conflicto: `ON CONFLICT (col1, col2)` necesita un índice único que coincida exactamente (los índices parciales no funcionan).
- **Usa `EXCLUDED.columna`** para referenciar los valores que se iban a insertar; actualiza solo las columnas que realmente cambiaron para reducir la sobrecarga de escritura.
- **`DO NOTHING` es más rápido** que `DO UPDATE` cuando no se necesita una actualización real.

### Evolución Segura del Esquema

- **DDL Transaccional**: la mayoría de las operaciones DDL pueden ejecutarse en transacciones y revertirse (rollback): `BEGIN; ALTER TABLE...; ROLLBACK;` para pruebas seguras.
- **Creación de índices concurrentes**: `CREATE INDEX CONCURRENTLY` evita bloquear las escrituras, pero no puede ejecutarse dentro de transacciones.
- **Los valores predeterminados volátiles causan reescrituras**: añadir columnas `NOT NULL` con valores predeterminados volátiles (ej. `now()`, `gen_random_uuid()`) reescribe la tabla completa. Los predeterminados no volátiles son rápidos.
- **Elimina las restricciones antes que las columnas**: `ALTER TABLE DROP CONSTRAINT` y luego `DROP COLUMN` para evitar problemas de dependencias.
- **Cambios en la firma de funciones**: `CREATE OR REPLACE` con argumentos diferentes crea sobrecargas (overloads), no reemplazos. ELIMINA (DROP) la versión antigua si no deseas la sobrecarga.

## Columnas Generadas

- `... GENERATED ALWAYS AS (<expr>) STORED` para campos calculados e indexables. PG18+ añade columnas `VIRTUAL` (calculadas al leer, no almacenadas).

## Extensiones

- **`pgcrypto`**: `crypt()` para el hashing de contraseñas.
- **`uuid-ossp`**: funciones alternativas de UUID; prefiere `pgcrypto` para proyectos nuevos.
- **`pg_trgm`**: búsqueda de texto difuso con el operador `%`, función `similarity()`. Indexa con GIN para acelerar `LIKE '%patron%'`.
- **`citext`**: tipo de texto insensible a mayúsculas. Prefiere índices de expresión sobre `LOWER(col)` a menos que necesites restricciones insensibles a mayúsculas.
- **`btree_gin`/`btree_gist`**: permiten índices de tipos mixtos (ej. índice GIN en columnas JSONB y de texto a la vez).
- **`hstore`**: pares clave-valor; mayormente superado por JSONB pero útil para mapeos de cadenas simples.
- **`timescaledb`**: esencial para series temporales: particionado automatizado, retención, compresión y agregados continuos.
- **`postgis`**: soporte geoespacial completo más allá de los tipos geométricos básicos: esencial para aplicaciones basadas en la ubicación.
- **`pgvector`**: búsqueda de similitud de vectores para embeddings.
- **`pgaudit`**: registro de auditoría para toda la actividad de la base de datos.

## Guía de JSONB

- Prefiere `JSONB` con índice **GIN**.
- Predeterminado: `CREATE INDEX ON tbl USING GIN (col_jsonb);` → acelera:
  - **Contención** `col_jsonb @> '{"k":"v"}'`
  - **Existencia de clave** `col_jsonb ? 'k'`, **alguna/todas las claves** `?|`, `?&`
  - **Contención de ruta** en documentos anidados.
  - **Disyunción** `col_jsonb @> ANY(ARRAY['{"estado":"activo"}', '{"estado":"pendiente"}'])`
- Cargas de trabajo pesadas de `@>`: considera la clase de operador (opclass) `jsonb_path_ops` para índices de solo contención más pequeños y rápidos:
  - `CREATE INDEX ON tbl USING GIN (col_jsonb jsonb_path_ops);`
  - **Compromiso (Trade-off)**: pierde el soporte para consultas de existencia de clave (`?`, `?|`, `?&`)—solo admite contención (`@>`).
- Igualdad/rango en un campo escalar específico: extrae e indexa con B-tree (columna generada o expresión):
  - `ALTER TABLE tbl ADD COLUMN precio INT GENERATED ALWAYS AS ((col_jsonb->>'precio')::INT) STORED;`
  - `CREATE INDEX ON tbl (precio);`
  - Prefiere consultas como `WHERE precio BETWEEN 100 AND 500` (usa B-tree) sobre `WHERE (col_jsonb->>'precio')::INT BETWEEN 100 AND 500` sin índice.
- Arrays dentro de JSONB: usa GIN + `@>` para contención (ej. etiquetas). Considera `jsonb_path_ops` si solo realizas contención.
- Mantén las relaciones principales en tablas; usa JSONB para atributos opcionales o variables.
- Usa restricciones para limitar los valores JSONB permitidos en una columna, ej. `config JSONB NOT NULL CHECK(jsonb_typeof(config) = 'object')`.

## Ejemplos

### Usuarios

```sql
CREATE TABLE users (
  user_id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  email TEXT NOT NULL UNIQUE,
  name TEXT NOT NULL,
  created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE UNIQUE INDEX ON users (LOWER(email));
CREATE INDEX ON users (created_at);
```

### Pedidos

```sql
CREATE TABLE orders (
  order_id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  user_id BIGINT NOT NULL REFERENCES users(user_id),
  status TEXT NOT NULL DEFAULT 'PENDING' CHECK (status IN ('PENDING','PAID','CANCELED')),
  total NUMERIC(10,2) NOT NULL CHECK (total > 0),
  created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX ON orders (user_id);
CREATE INDEX ON orders (created_at);
```

### JSONB

```sql
CREATE TABLE profiles (
  user_id BIGINT PRIMARY KEY REFERENCES users(user_id),
  attrs JSONB NOT NULL DEFAULT '{}',
  theme TEXT GENERATED ALWAYS AS (attrs->>'theme') STORED
);
CREATE INDEX profiles_attrs_gin ON profiles USING GIN (attrs);
```
